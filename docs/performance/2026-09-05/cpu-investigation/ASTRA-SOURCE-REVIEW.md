## Conclusions and limits

There are two verified mechanisms that can add main-process motion-analysis work: retirement of the pre-pipeline quiet-frame gate, and increasing the continuous evidence window from three to four frames. Neither establishes the fraction of observed CPU increase attributable to that mechanism. The frame preparation operations preceded the old gate, so removing the gate did not newly introduce resize/grayscale/blur on those frames. It introduced the qualification and downstream bookkeeping that the gate bypassed.

The two cameras with detection and recording disabled still qualify frames because eligibility is based on motion policy and diagnostic/observation demand, not detection eligibility. They are enabled live cameras, not stopped cameras. Their preparation and qualification have real consumers, principally the continuing scene model, qualification caches, and optional debug/route evidence. Most are not required for live viewing or recording. Disabling all preparation without resolving re-enable semantics and debug demand would nevertheless change behavior. Existing data do not measure the available CPU savings or attest current debug-lease state.

Existing timers are sufficient for a smaller first attribution step than a new profiler. In particular, per-stage qualification wall timings already run on every pipeline invocation despite `include_telemetry=False`. They are not exported by the owner-only socket. An existing diagnostic session, if one overlaps the windows, may already contain preparation, qualification and limiter summaries. Its presence must be checked, not assumed.

Subsequent evidence review: inspected `aligned-original-cpu.json`, its `evidence.py` accounting implementation, and `existing-diagnostic-inventory.json`. The common capture-relative 360–1740 second selection contains 275 service intervals per capture (1375.0/1376.3 seconds). Service CPU is 2.41685→3.14348 cores; main-process CPU is 1.73207→2.43861 cores, a +0.70654-core change accounting for approximately 97% of the +0.72663-core service difference. Capture workers are 0.49059→0.49597, recorder workers 0.07668→0.07877, and object workers 0.01207→0.01494 cores. This localizes the adverse difference primarily to the main process and is consistent with the source mechanisms above, but it does not identify a particular motion stage or remove scene/process-age confounding. The cgroup-minus-observed-process residual must remain unattributed. go2rtc is a separate dependency and not part of the service total. The accounting handles PID/start-time identity, positive intervals, cgroup resets, and observed newly born processes; processes that both start and exit between polls remain absent from process attribution. The tiny negative go2rtc residual is consistent with asynchronous reads and must not be assigned to a negative-cost task.

The bounded indexed diagnostic inventory found zero persisted diagnostic sample rows in both original capture windows. Therefore these existing timers cannot be recovered for those windows through that table; the hypothetical historical-diagnostics route below is exhausted for them. This does not establish that debug visualization was disabled, or that no diagnostic state existed outside those windows.

## Execution change and additional quiet-cycle work

`motion_analysis_service.py:471` admits a sampled frame using stop state, `frame_analysis_required()`, and the sampling interval. `:489` always resizes to the configured maximum dimension, converts to gray, and caches Gaussian blur for `gray_blur` (`motion.py:33`). It retains grayscale, color, processed and generation-tagged evidence references (`:535`). The worker then calls frame observation and tests the qualification cadence (`:945`). The shared limiter is acquired at `:974`; it is not a preprocessing limiter.

The old `analyze_continuous` compared the last two color frames converted to grayscale, took `absdiff`, counted pixels whose value changed by more than five, and returned when the ratio was below `temporal_filter_threshold`. It updated the cadence timestamp and, in camera_rescue mode, evaluated two readiness conditioners using a synthetic rejected result. That gate sat after preparation and acquisition of an analysis slot. The diff removes it altogether; the compatibility setting and skip counter remain but have no filtering effect.

The new path at `:1040-1137` reuses prepared derivatives and runs the actual qualification pipeline, updates the last result and qualification history, increments continuous/illumination counters, then considers visual backup and optional route candidate persistence. For inherited empty stage lists the resolved graph is adaptive (`motion_pipeline/configuration.py:149-171` and `defaults.py:6`):

The four-frame window is a separate change (`motion_analysis_service.py:167-176`). At full window size there are three transitions versus two before. Adaptive background and masks therefore have one more transition to process even for invocations that would already have passed the old gate. Historical-learning guards do not remove this cost. This is a 50% increase in the number of transition slots per full invocation, **not** a measured 50% stage or process CPU increase. Changed cadence, overlap, masking, array size, cache behavior and scene contents matter. The classic scorer needs four frames; any future optimization of adaptive history must preserve its own scoring/learning semantics rather than blindly reducing the global ring.

The reason not to reinstate the gate unconditionally is concrete: unchanged foreground pixels can differ from the learned background and require stationary learning. The old gate compared consecutive frames and could starve that update. The committed regression `tests/test_motion_analysis_service.py:1015-1073` checks that repeated quiet stationary foreground advances the background; this report inspected but did not execute it. Other committed regressions check real quiet results and readiness (`:1078`, `:1129`).

If a profiler is needed, specify tool availability, sampling rate, target PID, fixed duration and stop threshold before execution; no credible measured overhead can be asserted without that choice.
4. True persisted-event/attempt latency needs additional bounded correlated stage stamps if it remains a goal: capture/receipt, qualification completion, admission, attempt ready/start, compute complete, event transaction completion, refinement checkpoint and delivery completion.
